# Observability

Metrics, dashboards and alerts for every Faultline service that runs as a server, from one shared kit. The point is not the dashboards. It is that every failure mode this repository demonstrates, the stalled outbox relay, the celebrity fan out, the consumer falling behind, now has a number that shows it and an alert that fires on it.

## What is covered

Six programs publish metrics: the rate limiting lab's demo server, the URL shortener, the notification platform, the social feed, the payment platform, and the interactive lab's server. The other eight labs are libraries and command line demos with no long running process to scrape, so there is nothing for Prometheus to do with them and they are deliberately left alone.

| Piece | Where |
|---|---|
| The Go metrics library, in one canonical copy | `kit/go/obs` |
| Scrape config, recording rules, alert rules, and unit tests for the alerts | `prometheus/` |
| Dashboards, generated by a script | `grafana/` |
| Prometheus and Grafana in Docker | `docker-compose.yml` |
| Start every service, generate traffic, run everything end to end | `scripts/` |

## Run it

```bash
# 1. Every service, each on its own port (they all default to 8080)
pip install -r systems/payment-platform/requirements.txt
observability/scripts/run-services.sh

# 2. Traffic, in another terminal
python3 observability/scripts/traffic.py --seconds 300

# 3. Prometheus and Grafana, in a third
docker compose -f observability/docker-compose.yml up
```

Grafana is at http://localhost:3000 with two dashboards, **Faultline: service health** and **Faultline: what each system is doing**. Prometheus is at http://localhost:9090. The services listen on 127.0.0.1, which Docker Desktop on a Mac reaches through `host.docker.internal`. On Linux, start them with `0.0.0.0` addresses instead, or run Prometheus on the host.

## What every service publishes

The three HTTP metrics have the same names and labels in Go and in Python, so one dashboard and one set of alerts covers all of them.

| Metric | Meaning |
|---|---|
| `http_requests_total` | Requests by method, matched route and status code. |
| `http_request_duration_seconds_bucket` | Latency histogram by method and route. The buckets are the same in every service. |
| `http_requests_in_flight` | Requests being handled right now. |
| `up` | Whether Prometheus could scrape the service. |
| `go_goroutines` | Go services only. A count that only climbs is a leak. |
| `go_memstats_alloc_bytes` | Go services only. Heap in use. |
| `obs_collector_errors_total` | A scrape time collector failed and was skipped, instead of breaking the page. |

The route label is the pattern the router matched, `/timeline/` or `/payments/{idempotency_key}`, never the URL. A URL carries user ids and idempotency keys, and one series per id is how a metrics system gets taken down. The Go kit also caps any labeled metric at 500 series and folds the rest into one `overflow` series, as a backstop.

## What each system adds

| Metric | System | What it shows |
|---|---|---|
| `payments_created_total` | payment platform | Payments newly created. |
| `payments_deduplicated_total` | payment platform | Retries answered from an existing payment: charges that did not happen twice. |
| `payments_outbox_pending` | payment platform | Events committed but not yet published. |
| `payments_outbox_oldest_pending_age_seconds` | payment platform | How long the oldest one has waited. The stalled relay detector. |
| `payments_outbox_dispatched_total` | payment platform | Events the relay has published. |
| `notification_delivered_total` | notification platform | Notifications delivered. |
| `notification_queue_depth` | notification platform | Waiting to be delivered. |
| `notification_dead_letter_queue_size` | notification platform | Notifications that exhausted their retries. |
| `socialfeed_inbox_writes_total` | social feed | Per follower inbox writes, the fan out cost. |
| `socialfeed_strategy_info` | social feed | Which timeline strategy is running. |
| `urlshortener_cache_hits_total` | URL shortener | Resolves served from the cache. |
| `urlshortener_cache_misses_total` | URL shortener | Resolves that read the store. |
| `ratelimit_algorithm_info` | rate limiting lab | Which algorithm the server runs. Allowed and rejected are the 200 and 429 series of `http_requests_total`. |
| `labserver_kafka_total_lag` | interactive lab server | Consumer lag, from the real Kafka lab. |
| `labserver_kafka_partition_lag` | interactive lab server | The same, per partition. |
| `labserver_kafka_produced_total` | interactive lab server | Messages produced. Restarts from zero when the session is reset. |
| `labserver_kafka_consumed_total` | interactive lab server | Messages consumed. |

Most of these are read from the service's own counters when Prometheus scrapes, so the service code did not have to change. The one place that needed a line of code is the payment platform, which counts created and deduplicated payments where it knows which happened.

## The alerts

Each alert is tied to a failure mode the repository demonstrates. The thresholds are illustrative, chosen for the demo traffic. A real service would set them from its own SLOs.

| Alert | Fires when | The failure it is for |
|---|---|---|
| `InstanceDown` | a target cannot be scraped for a minute | A service is down, or its `/metrics` is. |
| `HighErrorRatio` | more than 5% of requests are 5xx, with enough traffic to mean it | A service is failing. |
| `HighLatencyP99` | p99 above 250ms for ten minutes | A service is slow. |
| `PaymentOutboxStuck` | the oldest outbox event is over 30 seconds old | The relay stopped: payments commit, nothing is announced. |
| `NotificationDeadLetterQueueGrowing` | more than five dead letters in ten minutes | A channel is failing. |
| `NotificationQueueBacklog` | over 1000 notifications waiting for five minutes | Delivery cannot keep up. |
| `SocialFeedFanoutAmplificationHigh` | over 1000 inbox writes per post, on average | The celebrity problem, under fan out on write. |
| `URLShortenerCacheHitRatioLow` | under half of resolves hit the cache | The cache is too small or the traffic too flat. |
| `KafkaConsumerLagGrowing` | lag above 100 and still rising | Consumers cannot keep up with producers. |

The fan out alert looks at the average over all posts, so one celebrity among many ordinary posts is diluted. It fires when the celebrity is large enough to dominate the average, which is the case that matters, and it is the first alert to refine if the traffic mix changes.

## How it was verified

Four layers, because each catches what the others cannot.

**The library** has unit tests for the exposition format, escaping, the series cap, concurrency, and the middleware. Its output also passes `promtool check metrics`, Prometheus's own linter, and parses correctly with the official Python client's parser, an independent implementation.

**The rules** are unit tested with `promtool test rules`. Every alert has a case where it must fire and cases where it must stay quiet, such as too little traffic to call a trend.

**The names** are cross checked by `scripts/check-metric-names.py`: every metric a dashboard or a rule uses must be defined in code. A rename that misses one side fails CI, instead of quietly emptying a panel.

**The whole stack** runs in `scripts/e2e.sh`, which needs no Docker. It starts every service, a real Prometheus, and traffic. It lints every service's page, runs every dashboard query against live data, then stops one service on purpose and checks that the right alerts fire for real conditions and the others stay quiet. It uses a one second scrape interval and five second alert delays so a run takes about two minutes. The rules are otherwise the ones in `prometheus/rules`.

```bash
PROMETHEUS=/path/to/prometheus PROMTOOL=/path/to/promtool observability/scripts/e2e.sh
```

That script found two real problems while this was being built: services that served a 404 on `/metrics` because the line that wires the kit in had not been applied, which unit tests that exercise the kit in isolation could not see, and a traffic mix that drowned the celebrity in ordinary posts. `scripts/check-obs-sync.sh` now fails CI if a service carries the kit but never calls `observe(...)`.

## Decisions worth knowing

**The kit is copied, not imported.** Faultline's labs and systems never import each other, so each carries its own copy of `kit/go/obs` in `internal/obs`. That costs duplication and buys modules that stay self contained and runnable alone. `scripts/sync-obs.sh` writes the copies from the canonical source, and CI fails if one has drifted, so there is still one source of truth. Edit `kit/go/obs`, run the script, commit the result. `modules.txt` lists who carries a copy.

**The Go kit is hand written, and says so.** It speaks the Prometheus text format without depending on the official client, so the modules stay free of third party dependencies. It does the counters, gauges and histograms these services need, and none of summaries, exemplars, native histograms or gzip. The Python service uses the official client, and a test checks that its names, labels and latency buckets match the Go kit. If a service ever needs more than this covers, switching it to the official client is the right move, and the dashboards would not change.

**Counters must end in `_total`, and a labeled metric is capped.** Both are enforced at registration, because a mistake in either is silent until it is expensive.

**Scrapes are not traffic.** `/metrics` is left out of the request metrics, or every rate would include the scrape rate.

**Long lived streams are left out of the latency histogram.** The interactive lab's event stream counts as a request, but its duration is how long a browser tab stayed open, which would bury every real latency.

## Not built

Tracing. An OpenTelemetry layer would add a dependency to every module, which is the opposite of what the kit is for, and metrics answer the questions this repository asks. Log aggregation. Alert delivery, so nothing receives these alerts: there is no Alertmanager. And the Docker stack and the Grafana dashboards have not been run: the compose file only parses, and the dashboards are checked by running every one of their queries against Prometheus, not by loading them into Grafana.
