# Writing style

Every piece of documentation in this repository, including code comments where it matters, answers four questions:

1. Why does this exist?
2. What breaks without it?
3. What does it cost?
4. What trade-off does it introduce?

## Rules

- No claim without evidence. If a number wasn't measured, it's labeled "expected, not yet run," not stated as fact.
- No company's architecture is described unless there's a public source for it. Otherwise, call it an educational simplification or a reasonable inference, and say so.
- Prefer a short, direct sentence over a longer one that says the same thing.
- Skip the filler. No "in today's world," no "seamless," no calling something production-grade instead of showing why it is.
- A README that can't say what breaks without a component isn't done yet.
